# Example: generated code

A C program whose message structs are generated from TOML specs by a Python generator, and whose keyword lookup is generated by gperf, an external tool. It shows how Facere tracks a generator's own code, a generated header that compiles need before they run, and a program the build only sometimes needs. Compiling needs `uv`, whose `uvx` runs the compiler, and `keywords` needs `gperf`.

```
fac.py
messages/login.toml
messages/greeting.toml
src/keywords.gperf          gperf's keyword table
src/keywords.h              declares the lookup gperf generates
src/main.c                  includes messages/greeting.h and src/keywords.h
src/session.c               includes messages/login.h
tools/messages.py           the message generator, plain Python
```

A spec such as [`messages/login.toml`](./messages/login.toml) lists a message's fields. [`tools/messages.py`](./tools/messages.py) knows nothing of Facere: its `generate` function takes three paths and writes two files.

Each spec in [`fac.py`](./fac.py) names its outputs while `fac.py` loads, one header and one source, so every generated file is a declared output and each generated source compiles on its own. `message` calls the generator as a Python function, not as a command, so the generator's code joins each rule's fingerprint as the recipe's own code does, and `C_TYPES` by value, as every module constant the code reaches is. Its `open(spec)` reads a declared input, which passes the undeclared-path check, the failure of a recipe that uses an undeclared file under the root.

Every compile takes the generated headers as `fac.OrderOnly` inputs, so the first run generates them before any compile starts, and later runs re-execute a compile only for the headers its depfile listed, reported through `fac.add_inputs`. Generated sources land in `build/gen/`, which `fac.sources("src/**/*.c")` never reaches, and their objects stay beside them, since `fac.out()` keeps a path already in the output directory.

| Action | Executes | Why |
|---|---|---|
| `fac` | 2 `message` rules, `keywords`, 5 compiles, the link | Nothing is recorded yet |
| `fac` | none | Every fingerprint matches |
| Add a field to `messages/login.toml`, then `fac` | login's `message`, 2 compiles, the link | Only login's rule inputs the spec, and of the hand-written files only `session.c`'s depfile lists `login.h` |
| Add a comment to `tools/messages.py`, then `fac` | none | Fingerprints hash the syntax tree, which holds no comments |
| Change the generated text in `tools/messages.py`, then `fac` | 2 `message` rules, then the compiles whose headers or sources changed, and the link | The generator's code is part of each rule's fingerprint |
| Refactor `tools/messages.py` without changing its output, then `fac` | 2 `message` rules | Identical outputs leave every compile up to date |
| Add `messages/logout.toml`, then `fac` | logout's `message`, 1 compile, the link | The glob lists a new spec, the program gains an object, and a new order-only path changes no other compile's fingerprint |
| Edit `src/keywords.gperf`, then `fac` | `keywords`, 1 compile, the link | The table feeds only the generated `keywords.c` |
| Add `login.h` at the root, then `fac` | the 2 compiles that read a `login.h` | A new file named as a file a compile read may shadow it on an include path. This one does not, so the objects stay the same and the link stays up to date |
| Drop `headers` from `object_file`, then `fac` | a compile, failing, naming the rule that outputs the header it read | Nothing orders that compile after the generator, so it could race on the header |
| Have `message` run `tools/messages.py` through `fac.run`, then `fac` | `message`, failing, naming the path | No fingerprint would hold the generator's code then, so a `fac.Input` must declare it, and the file would need a command-line entry, which it lacks |
| Uninstall gperf, then `fac` | none | A missing program fails only a rule that must execute |
| Then edit `src/keywords.gperf` and `fac` | `keywords`, failing | `fac.run` names `gperf` as not found on `PATH` |

- **Generators that choose their own output names**, such as protoc emitting a file per service, need their outputs derived while `fac.py` loads. Otherwise the generator outputs a directory and one rule compiles everything in it, losing per-file rebuilds for that directory, the gap ninja's `dyndep` fills.
- **Every compile waits for every generated header** on the first run, since `headers` orders them all before any compile.
- **`-Ibuild/gen`** joins its path to the flag without `=`, so the undeclared-path check cannot see it. Here that costs nothing, since the generated headers are already inputs.
