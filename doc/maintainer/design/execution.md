# Execution

## Commands

`fac.run` spawns its arguments directly, never through a shell, so nothing needs quoting and nothing differs between platforms' shells. A spawn costs about a millisecond on Linux and several on Windows, against tens to hundreds of milliseconds per compile.

A rule's command runs in a session of its own, on Windows a process group of its own, with no terminal and an empty stdin, unless `stdin=` names a file, so a command that would prompt, such as `sudo` asking for a password, fails at once instead of waiting behind captured output. sudo caches a password per terminal, so a command needing it relies on a sudoers entry that asks for none. A command running `LIVE`, as a task's do by default, runs in Facere's foreground process group with the terminal instead, so they can prompt and an interrupt reaches them directly. On Windows a rule's live command keeps a process group of its own, so a graceful stop lets it finish, and since that group ignores the console's Ctrl-C, Facere's interrupt kills it instead. A command `fac.capture` runs in a task runs as a rule's does, since its output is captured.

When Facere's own stderr is a terminal, a rule's command gets a pseudo-terminal as its stderr instead of a pipe, so a compiler colors its diagnostics as it would unwrapped. Its stdout stays a pipe, so what a recipe reads from it never depends on whether Facere had a terminal, and its stdin stays empty. Facere opens the pty's terminal end with `O_NOCTTY`, so it never becomes the command's controlling terminal and a prompt still fails at once, and clears `OPOST` on it, so the kernel's newline translation leaves the output unaltered. The pty takes Facere's window size as the invocation starts, so a tool that wraps diagnostics wraps them as it would unwrapped. Facere reads the other end into the same capture the pipe would fill, printed whole when the rule finishes, and treats `EIO` there, which Linux returns once the command closes its end, as end of output. A recipe that passes `stderr=` gets its file, as always. Windows has no stderr-only pseudo-terminal, since ConPTY replaces a process's whole console, so there a rule's stderr stays a pipe.

## Environment

Every command inherits Facere's own environment, so a task's debugger, pager, or serial monitor sees the terminal's `TERM`, a GUI sees the display, and git sees the SSH agent. None of it joins the fingerprint, so opening a new shell re-executes nothing. A variable that changes an output is written in Python instead, through `env=` for one command or `fac.env(**values)` for every command, where `None` unsets a variable, the only way to narrow what a command inherits. An option for a clean environment would be additive, so none ships until a project needs one. Any `fac.py` may call `fac.env`, and every call applies project-wide, so calls may repeat a variable's value but never change it: one that does fails collection, naming both calls, rather than letting whichever loads last silently win.

Where a tool's own setup script computes variables the tool requires, as Visual Studio's does, a rule runs that script and records the variables in a file every consumer inputs and relays through `env=`, so they are fingerprinted by content and do not depend on the shell `fac` started in.

## Package-managed tools

A tool a package manager installs, such as pytest in a uv project, runs through the manager's command that syncs the environment before running, as in `fac.run("uv", "run", "--locked", "pytest")`, and its rule inputs the lockfile. The environment then matches the lockfile whenever the rule executes, even after a task rewrote the lockfile earlier in the same invocation. A manager without such a command gets an install rule that records what it installed, as [best practices](../../user/7-best-practices.md#stamp-files) shows for npm, and the tool's rules input that record.

## Scheduling

- **Jobs.** Declared outputs make parallel execution safe, so the default is every CPU the process may use: its affinity set where the OS exposes one, else `os.cpu_count()`, capped by a cgroup CPU quota so CI containers do not oversubscribe. Workers are threads, since a command releases the GIL while its process runs, so a recipe doing heavy Python computation spawns a subprocess for it. The main thread executes no recipe: it checks rules until the first is stale, then waits on the workers, since only it receives signals. A worker handed a stale rule starts another, up to the job count, unless one waits idle, so a build that executes one rule asks for no CPU count and starts one thread. A tool that runs its own workers, such as `pytest -n` or a parallel link, gets an explicit count from its recipe, and a [pool](./fac-py.md#rules-and-tasks) keeps such rules from overlapping, as in ninja.
- **Ordering.** Targets are built batch by batch in the order the requirements set out, collecting again after each batch that executed a task that more targets follow, as [collection](./collection.md) describes. A task executes alone on a thread of its own, once every rule it inputs is current, and `fac.give_lock()` asks the main thread, which commits the state and gives the lock while the task goes on. GNU make processes goals in order only without `-j` and races with it, which the Linux kernel's Makefile works around by running one `make` per goal.
- **Existing outputs.** Facere leaves an existing output in place when its rule executes, since most tools, compilers included, overwrite theirs, and deleting thousands of object files first would buy nothing.

## Failure

The first failure stops new jobs, running jobs finish, and Facere exits with status 1, as it does when a store's method raises, since a store's code is the project's own. Each failure prints as it happens, and a failure stops the invocation before the targets after it. `-k` instead builds everything not downstream of a failure, and executes a task only where every rule it inputs succeeded or was current. An interrupt kills every running command's session, since a command in a session of its own never sees the terminal's `SIGINT`, and ends the invocation after at most a second more for the recipes whose commands it killed, since Python cannot stop a thread, so a recipe looping in Python is abandoned with its rule unrecorded. SIGHUP interrupts the same way, then ends Facere with SIGHUP once the terminal is restored. SIGTERM on Linux and macOS, and `CTRL_BREAK_EVENT` on Windows, ask for a graceful stop instead: no new job starts, running rules finish, their stores are written, and they are recorded, and a task's commands get the same signal, then are killed after 10 s. On Windows the stop spares a rule's commands only as a `CTRL_BREAK_EVENT` sent to Facere's process group, as a parent process sends it and watch mode stops a cycle. Ctrl+Break typed at the keyboard reaches every process on the console whatever its group, so it ends a rule's live command too. `kill`, `docker stop`, and a cancelled CI job therefore keep every finished compile, and a parent process can stop Facere without a terminal. A graceful stop exits with `143`, as [the exit statuses](./command-line.md#exit-statuses) list. A task that fails after a graceful stop was asked for counts as stopped, since its commands took the same request.

A failed or interrupted rule has its recorded fingerprint cleared and its outputs left as the recipe left them, so a half-written object file re-executes next time and stays available for inspection meanwhile.

## Output

Each rule's command output, stdout and stderr both, is captured and printed whole and unaltered when the rule finishes, so parallel output never interleaves, while `fac.capture` still returns the stdout. A recipe's own Python output, such as `print()`, is captured per rule the same way, in the order written beside its commands' output, while a thread the recipe starts prints live, since no write tells its thread's recipe. A rule's command running `LIVE` holds the terminal while it runs: it shares Facere's streams, what its recipe wrote before it prints first, so the rule's output keeps its order, and other rules' output waits until it exits. `ON_FAILURE`, or `-q`, holds a successful command's output back entirely. A task's output is shown live instead, and its failure report names the task and the failing command without repeating what was shown. A command `fac.capture` runs in a task writes to pipes rather than the terminal.

Facere's own output goes to stderr, so stdout carries only what commands and recipes wrote and what `--inputs`, `--outputs`, `--list`, `--check`, `--docs`, `--python`, and `--version` print. Which of it a caller may parse is in [the command line](./command-line.md#contract).

A failure prints the failing command or exception, its stderr and stdout, and the tail of any file its `stdout=` or `stderr=` filled, then names the rule and its `fac.py:line`.

On a terminal, one status line shows progress, paused while a task runs or a rule's command holds the terminal. When stderr is not a terminal, Facere prints no color and no status line. With `-C`, and around the shown output of a rule whose command used `cwd=`, Facere prints `fac: Entering directory '<absolute path>'` and a matching `fac: Leaving directory` line, as make does, so relative paths in a tool's diagnostics resolve. The warning that assertions are disabled, through `-O` or `PYTHONOPTIMIZE`, is one line, as is the one for rules that a [change during their recipes](./fingerprints.md#changes-during-a-recipe) left stale twice in a row, which counts the rules it does not name.
