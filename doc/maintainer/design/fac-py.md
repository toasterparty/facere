# The `fac.py` interface

doit, SCons, and waf already offer Python build scripts and content hashing. What Facere adds is in the [requirements](../requirements.md), and [getting started](../../user/1-getting-started.md) shows a complete `fac.py`.

The files are named `fac.py` because a `facere.py` would shadow the `facere` package in editors, which resolve a project's own modules before installed ones, breaking completion in every `fac.py`. `import facere as fac` makes the tool one name across `fac.py`, the `fac` command, and the code, as `np` does for numpy.

## Annotations

`fac.Input`, `fac.OrderOnly`, `fac.Output`, and `fac.Text` are `typing.Annotated` aliases of `str`, so a type checker sees plain strings. `fac.Input[fac.Virtual]` and `fac.Output[fac.Virtual]` hold a `fac.Virtual` instead, as [stores](./stores.md#interface) describes.

| Annotation | Holds | Facere uses it to |
|---|---|---|
| `fac.Input`, `list[fac.Input]` | files or directories the recipe reads | execute first the rules that output each one or a path inside it, require the rest to exist, and hash their content |
| `fac.OrderOnly`, `list[fac.OrderOnly]` | files or directories the recipe may read, such as a generated header only some compiles include | execute first the rules that output each one or a path inside it, require the rest to exist, and hash their content only once the recipe reports reading them. Their paths always join the fingerprint. A task declaring one fails collection, since a task records nothing |
| `fac.Output`, `list[fac.Output]` | files or directories the recipe writes and Facere tracks | rebuild them when changed or deleted by hand, reject two rules outputting one path, and execute this rule before any rule or task that inputs them |
| `fac.Input[fac.Virtual]`, `list[fac.Input[fac.Virtual]]` | virtual outputs of a [store](./stores.md) the recipe reads through `fac.read`, and [virtual sources](./stores.md#virtual-sources) | execute first the rule that writes each virtual output, hash their values, and call each virtual source's signature. A task declaring one fails collection, so a task reading a store can be designed later without changing what an accepted `fac.py` means |
| `fac.Output[fac.Virtual]`, `list[fac.Output[fac.Virtual]]` | virtual outputs of a store the recipe sets through `fac.write` | write them to their store once the recipe succeeds, rewrite them when changed or missing, and reject two rules writing one virtual output |
| `fac.Scope` | a scope from `fac.scope` | define the rule or task in that scope, as [names](./names.md#declaring-names) describes |
| `fac.Args` | on a task, the arguments after `--` | pass them as a tuple of strings |
| none, or any other | a value, such as a list of flags | hash it by value. On a rule, a string naming an existing file under the root, or a path a rule outputs, fails collection, naming the annotation to add, while a task's values go unchecked, since a task records nothing. A directory no rule outputs, such as a tool's cache, is a value |
| `fac.Text`, `list[fac.Text]` | data that may look like a path, such as the entries a manifest lists | hash it by value, skipping the path check, so reading a file it names is the recipe's own business |

A plain `str` annotation is a value like any other, path check included: an author annotating for a type checker must not switch the check off without knowing.

## Rules and tasks

- **Decorators.** `@fac.rule` and `@fac.task` return the function unchanged, so a recipe stays callable as plain Python, and may drop their parentheses. Both take `default=True`, `each=`, `values=`, and `name=` for a helper that names its rules after what they build. `@fac.rule` also takes `pool=`. No decorator option touches the terminal, since whether a command shares it is the command's own [console mode](#recipes). `always=True` executes its rules whenever they are built, for data Facere cannot see change, such as a download from a moving URL. `clear=True` deletes every output before the recipe executes, for a tool such as `ar r` or `uv build --out-dir` that keeps what an earlier execution left.
- **`each=` and `values=`.** `each=` is read once at decoration and takes one dict per rule or task, each key filling the parameter it names, so a row reads as the call it makes and a misspelled key fails collection, naming it. Positional tuples would save a few characters per row, but they push `zip`, tuple unpacking, and parameter order onto every author, and a dict costs nothing measurable at collection. `values={"cc": CC}` fills the parameters its keys name in every rule or task the decorator defines, so a helper passes shared values once, and a key that a row also names fails collection. Keyword arguments are Facere's options alone, so an option added later never captures a parameter of its name, as one shared namespace would, silently. Decorating one function twice, as a shipped helper does when a project calls it twice, defines both sets of rules.
- **Tasks.** A task executes with the terminal, so a long test run reports as it goes and a debugger works. Without a terminal, as in CI, its commands share Facere's own standard streams, so it executes the same unattended. A rule's command passing `console=fac.Console.LIVE` gets the same, for a step that needs a person, such as signing with a hardware-token PIN: its rule records its outputs like any rule, so it executes only when stale, and without a terminal, on both stdin and stderr, the command fails at once, naming its rule. One such command runs at a time, holding the terminal, while other rules execute on and their output waits.
- **Task arguments.** `fac test -- -k parser` forwards a filter to pytest, and `fac flash -- /dev/ttyUSB2` picks one of several boards. The task's own code decides what the arguments mean, typically falling back to a per-machine constant from a shared module kept out of version control, then to the tool's own default. Every task the targets reach that takes `fac.Args` receives the same arguments, and arguments after `--` that no task takes fail before anything executes.
- **Long-running tasks.** A task that keeps running, such as an app opened by hand or a dev server, calls `fac.give_lock()` so other invocations need not wait for it. The call waits for every rule its target needs to finish, commits the state, re-checks the outputs the invocation built, and releases the lock, which Facere takes back before any later target. Where an output changed after its rule finished, it raises instead and keeps the lock, since no later check could tell that change from another invocation's rebuild. From then on, another invocation may rebuild files the task is using. A second call does nothing, and a call from a rule fails the rule, since a rule's record needs the lock.
- **Pools.** `LINKS = fac.pool(2)` and `@fac.rule(pool=LINKS)` cap how many rules execute at once across every rule given that pool, as ninja's pools do, such as memory-bound links or a tool running its own workers. One function's rules and several functions' share the one form. A `threading.Semaphore` a recipe holds cannot serve, since a lock fails collection as a value.

## Recipes

Facere calls a rule's or task's function in a worker thread with the root as working directory. A generator or an `async def` fails collection, and a recipe returning anything but `None` fails, since such a body would never run as written, and a return value can be given a meaning later only if it fails now.

`fac.run(*args, cwd=None, env=None, stdin=None, stdout=None, stderr=None, timeout=None, console=None)` spawns one command, raises `subprocess.CalledProcessError` on a non-zero exit, and returns `None`. `console=` picks how the command meets the terminal:

| `fac.Console` | The command |
|---|---|
| `LIVE` | shares Facere's stdin, stdout, and stderr, so it prints as it runs and may prompt. A task's default |
| `AFTER` | is captured, its output printed whole once the rule finishes. A rule's default |
| `ON_FAILURE` | is captured, its output printed only where its failure fails the recipe |

In every captured mode a failing command's output travels only in the raised error, so a failure the recipe catches prints nothing, and no mode discards output. `fac.console(mode)` in a `fac.py` sets the default for the commands of the rules that file defines, as `fac.env` sets their environment, so a project chooses its own quiet without a flag, and an explicit `console=` overrides it. One parameter with three members replaces a decorator flag and a command's `quiet=`, which together could ask for a live command to be hidden. `fac.capture(*args, ...)` takes the same arguments but `stdout=` and `console=`, and returns the command's stdout decoded as UTF-8, printing nothing else on success, so a check of its output runs only after success. It behaves alike in a rule and a task: in a task its command runs as a rule's does, with no terminal and an empty stdin, so it cannot prompt. One function per purpose means a helper moved from a rule to a task keeps working, where a return value that depended on where it ran would turn empty without an error. `cwd` serves tools such as `zip` that store paths relative to where they run, and the command's relative arguments resolve against it for the undeclared-path check. `timeout` kills the command's session. Several commands are several calls. Both work on a recipe's own thread, and in a task from threads it starts, since a task executes alone. A call from a thread a rule's recipe started fails, since that thread cannot be told from another rule's while rules execute in parallel, and fails the rule too, whatever the recipe does with the error, as the undeclared-path check does. Facere tells such a thread by the audit event Python raises as a thread starts. `fac.capture` also works in a store's methods and a [`fac.trust`](./fingerprints.md#trusted-trees) stamp.

`fac.read_text(path)` and `fac.write_text(path, text)` read and replace a text file in UTF-8, and write `\n` line endings on every OS, since `open`'s defaults follow the locale and the OS, so a rule writing text with them gives different bytes on different machines.

`fac.write_archive(path, directory, top=None)` writes a `.zip`, `.tar`, or `.tar.gz`, chosen by `path`'s suffix, holding every file under `directory`, inside a directory named `top` or else `directory`'s own name. Members are sorted, times are fixed at the format's earliest, owners are empty, and modes are `0o755` for an executable file and `0o644` otherwise, so the same files give the same bytes on every machine, which `shutil.make_archive` does not.

`fac.load()` returns the value the rule passed to `fac.save(value)` at its last success, or `None`, so a recipe can remember what a server last sent, such as an ETag. It returns `None` too where any output no longer hashes as recorded, since a server answering the saved ETag with 304 would otherwise have the recipe keep a file edited by hand. The value is kept with the rule's record, which a failure clears, stays out of the fingerprint, and must be one Facere can hash.

## Paths

Every path a project writes, and every path Facere returns, is relative to the root, in every `fac.py`, shared module, and recipe, so a string means one file wherever it is written, computed, or passed. A declaration, a module constant, a flag such as `f"-I{INCLUDE}"`, and a recipe's `fac.run` arguments all agree with no conversion, and a shared module writes paths as plain literals.

`fac.here(path=".")` converts a path relative to the directory of the `fac.py` calling it, so `lib/fac.py` writes `fac.here("a.c")` for `lib/a.c`. It returns a plain string, which survives any string operation, and fails when called from any file but a `fac.py`, since a shared module or a recipe has no directory of its own. The cost is the call around each literal in a `fac.py` below the root, and none of the reference projects needs such a file. The alternative, paths relative to each `fac.py`, gave one string two meanings: a module constant reached a recipe unconverted and read the wrong file, and a root-relative path marked as such lost its mark through an f-string, both without an error.

`fac.out(path=".", suffix=None)` places a path in the output directory, mirroring its place under the root and optionally swapping its suffix, so `src/net/tcp.c` becomes `build/src/net/tcp.o`. A path already in the output directory keeps its place. `fac.out()` is the output directory itself, at collection and in a recipe alike, and a scope's output directory is reached only through its value, as `scope.out(path)`, described in [names](./names.md#declaring-names).

The output directory may lie outside the root, on a tmpfs or beside a read-only checkout. Facere records each path inside it relative to the output directory, so moving either rebuilds nothing, while a recipe receives such a path relative to the root, as `../` paths, or absolute across Windows drives. A value embedding one, such as a flag, changes when the two move apart.

`fac.sources(*patterns)` lists the files the patterns match, sorted, through Facere's own matcher rather than `glob.glob`, whose matching differs between platforms, and which cannot match the cached listings. A pattern matches alike on every OS: case-sensitive everywhere, `*` within one part of a path, `**` only as a whole part, matching any number of directories without entering a linked one, though a part naming a linked directory enters it. `?`, `[`, and `]` fail, reserved for later syntax, since matching them later would change what an old pattern lists. It skips hidden files unless the pattern's own part starts with `.`, so an editor's `.#main.c` lock never matches `*.c`. It skips the output directory and any other directory holding Facere's state, so a tree built with `--out build-ci` beside an older `build/` lists neither. It reads no ignore file: what a glob skips is written beside it in Python.

## Across files

- **Other `fac.py` files** are never imported. A `fac.py` names what another builds by writing the path, or through a constant both import from a shared module, and importing a `fac.py` fails, naming the shared module to move its constants into.
- **Shared code** is importable because the root is appended to `sys.path` during collection, after installed packages. The docs keep facts several `fac.py` files share, such as the project's configurations, in `tools/build.py`, imported as `from tools.build import ...`, which is easy to find from the root and clear of the PyPI package `build`. Code that drives Facere stays in `fac.py` files and extensions, and a component's own build settings live in an override in its own `fac.py`. A shared module defines rules and tasks only from functions a `fac.py` calls: it imports once, so rules defined at its import would take the names of whichever `fac.py` imported it first.
- **Overrides.** `@fac.override(function, match=None)` in a `fac.py` adjusts every rule `function` defines, from any `fac.py`, shared module, or extension, that has an input under that `fac.py`'s directory, limited, when `match` is given, to rules defined in a scope whose dotted name that pattern matches. Deleting the override reverts it, as a subclass refines a method its base never mentions. The decorated function is called once collection ends with each such rule, whose attributes are its parameters, and may reassign the rule's values and inputs, as in `rule.cflags = [*rule.cflags, "-Os"]`. Outputs stay fixed, since they identify a rule and key its record. Overrides apply shallower directories first, then in path order, and which rules an override receives is decided before any applies, so an input one adds never changes which others apply. `fac.rules`, validation, and fingerprints all see the adjusted values, so `compile_commands.json` records the flags actually used, and `--list` and `-v` name the overrides that changed a rule.
- **Introspection.** `fac.rules(function, under=None, match=None)` lists the arguments of every rule `function` defines, as dicts keyed by parameter name, with every path root-relative, limited to rules with an output under the directory `under`, and to rules defined in a scope the pattern `match` matches. It returns a placeholder that Facere fills once collection ends, after overrides and before any hashing, so a rule taking it as a value sees the rules of every `fac.py` whatever the collection order. The placeholder is data about rules, so the path check never applies to it.

## Settings

Python binds a parameter's default when the rule is defined, so a rule defined in a loop keeps that pass's value, while it binds a closure variable or a module global only when the recipe executes, so every rule from the loop would see its last value. A module constant rebound after a rule reading it was defined, and a closure variable that is not a function, class, or module, therefore fail collection, naming the variable and the parameter to pass it through. A value that is `os.environ`, such as `ENV = os.environ` read by a recipe, fails collection too, naming the variable, since it would hash the whole inherited environment, which the requirements keep out of fingerprints, and a new shell would execute the rule.

A fact that differs between machines, such as where an SDK is installed, is not a setting: a rule fetches the tool into the tree, or locates it and records what it found in a file its consumers input. Facere reads no local settings file of its own: a project wanting per-machine settings imports them from a shared module it keeps out of version control.
