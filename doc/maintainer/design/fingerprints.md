# Fingerprints and checks

Timestamps cannot decide what is stale. `git checkout` stamps every file it touches with the current time, archive extraction and `cp -p` preserve old times, FAT stores them at 2 s granularity, and a changed compiler flag touches no file at all. Facere compares content fingerprints instead.

| Node | Declared by | Up to date when |
|---|---|---|
| Source | an input no rule outputs, a [store](./stores.md)'s virtual output included | always, and must exist |
| Rule | `@fac.rule` | its recorded fingerprint matches, its [added inputs](#added-inputs) are unchanged, and its outputs are intact |
| Rule that always executes | `@fac.rule(always=True)` | never, though rules downstream re-execute only when its outputs' content changed |
| Task | `@fac.task` | never: it executes whenever requested |

## What a fingerprint hashes

- its function's syntax tree without positions or docstring, and that of every function and class under the root its code names through a global, a closure variable, or a shared module's attribute, along with the function a decorator wraps, found through `__wrapped__`, and the classes under the root a class inherits from, so reformatting or editing a comment or docstring re-executes nothing
- for code under the root that a value holds, such as a dataclass whose methods the recipe calls or a dict of handlers, the syntax tree of that function or class and of all it reaches, as for code named. A lambda, which no name finds in its module, hashes as the syntax tree of the whole module defining it, which re-executes more than needed but never leaves a rule stale
- its values, the arguments its parameters other than inputs and outputs receive, and the module constants its code reads, a shared module's included, along with those of every function it reaches and the default arguments each such function binds at definition
- the variables `fac.env` sets for every command
- the Python minor version, as in `3.13`: a minor release may change what the same code does and how its syntax trees dump, and a patch release does neither
- the path and content of each input, where a file's content is its bytes and, on POSIX, its executable bit, and a link inside a directory input hashes as its target's content
- the path of each order-only input whose parameter the recipe's code names, never its content, since a recipe may derive flags from the list. One that never names the parameter cannot, so its paths stay out, and a list of generated headers that every compile orders after grows without re-executing them
- the path of each output by parameter, so swapping two outputs between parameters re-executes the rule
- the store, key, and value digest of each virtual input, and the code of the store of each virtual output

Hashing other rules' outputs, virtual outputs included, rather than whether those rules executed, means a rule that re-executes to identical bytes leaves everything downstream untouched.

Whether a recipe names an order-only parameter is read from its syntax tree, and a recipe naming `locals`, `vars`, `eval`, or `exec` counts as naming every parameter. Hashing every order-only path would need no such reading, and would execute every compile whenever a generated header is added, 8 rules for 3 in the `codegen` example, which is the case the annotation exists for. A second annotation for paths a recipe may not read would keep both guarantees too, and would give the interface two ways to say one thing.

A value hashes if pickle can take it apart, a rule Python users already know, so no list of types needs extending one project at a time. `None`, `bool`, `int`, `float`, `str`, and `bytes` hash by value, tuples and lists by element, dicts by item in insertion order, and sets and frozensets sorted, since their iteration order varies with `PYTHONHASHSEED`. Functions, classes, and modules hash by qualified name. Any other value, a subclass of those types included, hashes as pickle's reduction takes it apart, at a pinned protocol: the callable that rebuilds it, which names its class, and the arguments and state that callable receives, each by these same rules. So a set inside a dataclass stays sorted, an `IntEnum` member never hashes as its bare `int`, and a compiled pattern hashes by its pattern and flags. A function or class a value holds joins the fingerprint as one the recipe names does, so an edit to the method of a dataclass whose instance a rule receives executes that rule. A value pickle refuses, such as an open file or a lock, fails collection, naming the type and pickle's reason, as does a value holding itself. A `pathlib.Path` fails too, asking for `path.as_posix()`, since paths in values are strings, which the undeclared-path check reads.

A default that a reached function binds hashes the same way, as a module constant does. The default's expression is in the syntax tree and what it evaluated to is not, so leaving defaults out would miss `mark=MARK`. `pattern=re.compile(PATTERN)` hashes by the pattern, which an edit to `PATTERN` changes, and every `object()` sentinel hashes alike, since what it means is in the code that compares against it.

## Added inputs

`fac.add_inputs(paths)`, called in a recipe after its tool has run, reports the files the recipe read, usually by parsing a depfile. They are recorded after each success and checked on the next invocation, as in ninja. Facere normalizes each path to root-relative with `/`, against the root's resolved path and keeping case, so a depfile's `src/a/../b.h` and MSVC's absolute paths need no cleanup. It keeps every report wherever it lies, system headers and a sibling checkout's included, so a project moving from make or ninja loses no rebuild, and the hash cache makes each file one stat per invocation however many rules report it. A report inside the output directory that no rule outputs is scratch, such as a header the recipe itself rewrote, so Facere keeps only its name, for shadowing below, since tracking it would execute the rule again after every execution. An SDK a project fetches belongs in a rule's output, pinned by a version in that rule's values, rather than outside the root. An order-only input the report lists joins the rule's record, and one it omits only orders the build, so a generated header declared on every compile of a library re-executes just the compiles that include it. A declared `fac.Input` always counts, so a recipe that reads one in Python never loses it. An added input that no longer exists makes the rule stale rather than failing as a missing source, while one missing when the recipe reports it fails the rule, since a rule that recorded it would never settle. Only a rule's recipe may report, since a task records nothing, and only files: a report naming a directory fails the recipe, since the name kept for shadowing, the scratch exemption, and the snapshot below are all written for files, and a directory a recipe reads is declared as a `fac.Input`, whose whole tree joins the fingerprint. Accepting directories later would be additive, and rejecting them later would not. The core parses no format of its own.

Facere also keeps the file name of every added input, those outside the root included, and a new file under the root with one of those names makes the rule stale, since a tool searching a path may find it first, as a new root `stdlib.h` would shadow the header a compile found. New files show up as the difference between the tree's listing and the saved one. An invocation saves the listing when it finds a difference and again as it ends, failed or not, if it executed anything, so a file a recipe wrote under the root never counts as new by the listing. Outputs are matched by name instead, wherever they lie: a declared output new at collection, and a file new in a directory output whenever its tree is hashed, since a generated header shadows as well as a hand-written one. The second waits for the hash cache, whose entries are the files each tree held when last hashed, so a file the walk meets without an entry is new. A listing kept for this alone would duplicate those entries, and one kept in the rule's record would be lost with it, so after a failed execution every file in the tree would read as new. An invocation that finds no difference and executes nothing pays one walk of the tree, and a false match costs one re-execute. A match forgets the rule's record at once, so it stays stale though this invocation's targets do not reach it. A project whose recipes report nothing never walks the tree.

When a rule reports an input that another rule outputs, and none of its own inputs is an output of that rule or a directory holding one, the invocation fails naming both: the first may have raced on it, and without the input the next one might too. A file inside a directory output counts as that rule's output, for a declared input as for a report, so an input naming one orders its rule after the directory's. A recorded added input that a rule now outputs orders the recording rule after that rule as soon as it is checked, as ninja's deps log does, so a report recorded while the file was a source never lets its rule be checked first.

## The hash cache

Each hash is cached against the file's size, mtime, ctime, and inode, as git's index does, so an untouched file costs one stat. A store's virtual output digests are cached against its stamp, so a `FileStore` of any size costs one stat too. ctime cannot be set by tools, which catches the same-size `cp -p` that mtime alone misses, and the writers of fixed mtimes, such as npm stamping every package file 1985-10-26 and reproducible archives. Windows keeps a change time too, read through a handle on each file, so the cache misses there what it misses on Linux, at a slower no-op than a directory listing alone would give.

An entry pairs its hash with a stat taken before the read, since a stat taken after pairs new timestamps with old bytes. It is racy, and rehashed rather than trusted, while its file last changed less than 2 s before the start of the invocation that recorded it, measured against that start rather than when the state was saved, minutes later. Timestamp granularity cannot be known, from ext4's timer tick to FAT's 2 s, so the margin is fixed. Every output is born racy, so an invocation with nothing stale rewrites its racy entries, letting them settle. A directory output is hashed by walking its tree through the same cache.

A stat proves nothing on a file system whose timestamps Facere cannot vouch for, so every entry on one is rehashed on every invocation, as a racy one is. Facere tells such a file system by its type, read once per device from the mount table on Linux and from the volume on Windows: a network one, such as NFS, SMB, or sshfs, whose client caches attributes and whose server keeps its own clock, any other FUSE file system, and FAT and exFAT, which store coarse times. A Windows network drive counts as networked whatever file system its server reports, since a share commonly reports NTFS. A no-op there reads every file it tracks on that mount instead of statting it, which suits a project on a removable drive or a network share. WSL's mount of a Windows drive counts as local, since its times come from the same machine's clock, and its reads are slow enough that rehashing a project there would exceed the no-op budget.

## Outputs

Declared outputs are what let Facere catch two rules writing one file and notice a recipe that succeeded without producing its file. Outputs are hashed after each success and re-verified on the next invocation, so an output edited, truncated, or deleted by hand gets rebuilt. What a rule declares is what Facere tracks: a rule unpacking a vendor toolchain can declare only its driver, and let the recipe's own check, such as an assertion on the driver's `--version` output, vouch for the rest.

Facere defaults to the check that cannot miss a change, and a cheaper one that can is the project's to choose. A fetched SDK declared as a directory output, such as ESP-IDF's tens of thousands of files, is verified in full on every invocation, so a hand edit anywhere in it rebuilds what used it, at one stat per file. A project that trusts a cheaper check, such as asking git what changed, will supply its own, through a mechanism not yet designed.

## Changes during a recipe

A rule's fingerprint is taken before its recipe starts, and that fingerprint, not one taken afterward, is what a success records. An added input in the rule's record keeps the hash taken as the rule was checked. An invocation is correct for the files as they stood when it started, and an edit made while it executes is caught by the next one: before recording a rule, Facere stats each declared input and recorded added input again, and leaves the rule unrecorded where a stat moved since its fingerprint, even if the content changed back, as after a `git switch` and back during a long recipe. That costs stats only for rules that executed.

A file first reported has no stat from the rule's fingerprint, and its tool read it before the recipe could report it. Before an invocation's first rule executes, Facere stats every file under the root outside the output directory, the files its listing walks anyway, and leaves a rule unrecorded where a file it first reported moved since that snapshot or was absent from it. A task's recipe takes no snapshot, since a task records nothing, so `fac clean` walks nothing. A rule output first reported compares with the stat the hash cache took when its rule finished, so a change to it undone before the recipe ends is caught too. No clock takes part, so a file system's granularity and a file server's clock matter no more than for any stat, and on a file system whose timestamps Facere cannot vouch for, the snapshot holds hashes instead. An invocation that executes no rule takes no snapshot. A file outside the root is outside what Facere owns, so its first report is trusted, as is one in a hidden directory or behind a linked directory, which the listing never enters.

A file a command writes under the root outside the output directory, which its recipe then reports, moved since the snapshot, so its rule is left unrecorded on every execution. Declared as the rule's output it is no added input, and inside the output directory it is scratch. A file the recipe wrote from Python itself is exempt, as in the undeclared-path check.

A rule left unrecorded executes again on the next invocation. One such execution prints nothing: a save made while a build runs is the everyday case, the user made it, and the next invocation settles it. Facere keeps the inputs that moved in its state, and when one of them moves again in the rule's next execution, the invocation prints a warning above its closing line:

```
fac.py:7:2: warning: rule 'tidy' (build/a.txt) stays stale: a.txt changed while its recipe executed, in this execution and its last
```

Twice in a row is what a recipe changing its own input looks like, such as a formatter run in place, and without the warning such a rule executes on every invocation with nothing to say why. The line states what happened and names no fix, since whether to declare that file as an output or to stop writing it is the project's decision. Rules that stay stale together share the one line, which names the first and counts the rest, so the invocation's own output stays within three lines. The price is a table in the state, and the same line for a user who saves one file during two executions of one rule in a row.

## Undeclared paths

A recipe using an undeclared file under the root fails, naming the parameter to add, so editing a generator script re-executes what it generates, and a fetched or built tool run without its input fails instead of going stale.

`fac.run` checks every argument, the program included, and each part of a flag split at `=` and `,`, as in `--output-file=build/x.c` and `-Wl,-Map=build/fw.map`, against the files under the root outside the output directory and every path a rule outputs, wherever it lies, a file inside a directory output included. A Python audit hook, as PEP 578 defines, sees each file the recipe's own thread opens for reading and checks it the same way. Facere installs the hook once per process, on the first invocation, since PEP 578 hooks cannot be removed, and checks an event only when raised on the thread of a recipe the active invocation is executing, so repeated `fac.main()` calls, a test suite's included, pay for one hook.

Exempt are:

- paths a parameter annotated `str` holds
- shared modules a recipe opens, as printing a traceback does. A command given one fails, since its code joins a fingerprint only where the recipe reaches it by name
- files that no rule outputs, outside the root, in the output directory, such as a depfile, or in a hidden directory, where `sys.executable` lies in a project's `.venv`
- files the recipe reported through `fac.add_inputs` before using them, which covers a recipe that discovers what to read in Python
- files the recipe itself wrote from Python earlier in its execution, such as an archive's extracted tree it verifies

Writes stay with the damage checks below, so a rule declaring only part of what it unpacks still executes. A task records nothing, so its commands and opens go unchecked, and a cleanup task may name any output without building it first.

## Undeclared writes

Facere cannot see what a recipe writes or deletes, so it checks for the damage instead. Before a rule executes, an input built earlier in the invocation whose hash no longer matches what its rule recorded, or that is gone, fails the rule without executing it, naming the input and its rule. At the end of an invocation, Facere re-checks every output it built, one stat each, and fails naming any whose content changed after its rule finished. One that vanished passes, since the next invocation rebuilds it, so `fac app clean` succeeds. Damage done before an output's rule executes, as when a fetch replaces a directory before the compile that writes into it, needs no check, since that rule rebuilds its output. An invocation with nothing to do builds nothing and re-checks nothing.

## Open risks

The user docs list these in [hidden inputs](../../user/7-best-practices.md#hidden-inputs), which changes with this list.

- **Values read at run time.** A recipe that reads an environment variable, or anything else besides files, while it executes leaves it out of the fingerprint.
- **Inherited variables** stay out of the fingerprint, so one that changes an output, such as `CPATH`, `LC_ALL` for `sort`, or `SOURCE_DATE_EPOCH`, goes unnoticed until the project writes it through `env=` or `fac.env`.
- **The standard library and Facere's own modules**, which recipes call, are hashed by name only, so upgrading Facere or a Python patch release re-executes nothing, unless the Facere release changes what a fingerprint holds.
- **What a store cannot see.** A store's `read` that skips part of its file, or a `stamp` that misses a change, leaves that part or that change untracked.
- **Unresolved code.** Code a recipe reaches through a computed name, as with `getattr(module, name)` or `importlib.import_module`, stays out of the fingerprint, as does an order-only path a recipe reads through its frame, as with `inspect.currentframe()`, without naming the parameter.
- **Programs** stay out of the fingerprint unless the project declares them, as an input or as a version in a value. Facere does not hash what a command launches on its own: that would see only the launcher, not `as` and `ld` behind `gcc` or zig behind `uvx`, and would rebuild everything when the launcher alone is upgraded.
- **Clock skew.** A racy entry is measured against the local clock, and a file's timestamps come from its file server, so a server behind by more than the margin makes a racy entry read as settled.
- **First reports the listing never walks.** A file outside the root, in a hidden directory, or behind a linked directory has no snapshot, so a change made to it while the recipe that first reports it executes goes unseen, as with a system header upgraded during its first compile.
- **File systems taken as local.** WSL's mount of a Windows drive, and any file system Facere does not know as networked or coarse, are trusted to show each change in a stat. The type cannot tell an overlay or union mount, such as a container's, laid over a network file system, a virtual machine's share of its host's files over 9p, virtiofs, or VirtualBox's vboxsf, whose times come from the host's clock, or a Linux device the mount table does not list. On an OS other than Linux and Windows, every file system is taken as local.
- **Reads that raise no `open` event**, such as `os.listdir`, `os.scandir`, `os.path.exists`, `os.rename`, and `sqlite3.connect`, escape the undeclared-path check.
- **Files looked for and absent**, as with `__has_include`, leave no name to shadow, so creating one makes nothing stale.
- **Orphans.** A file Facere stopped tracking stays in place and is a source to any rule that inputs it, so a consumer of a renamed output still builds, and a recipe that stops writing an output leaves the last execution's file, which Facere records.
- **Paths joined to a flag** without `=` or `,`, such as `-Ibuild/gen`, escape the undeclared-path check, as do files opened from threads a recipe starts itself.
- **Files a command wrote** under the root, outside the output directory, are not known as the recipe's own, so using one later in that recipe fails unless the recipe reports it first.
- **Shadowing the listing misses.** A new file in a hidden directory, the output directory, or behind a linked directory is never listed, and one a command writes under the root while an invocation executes counts as that invocation's own, so either can shadow a file a rule read without making the rule stale. An output outside the root, such as a header installed into `../sysroot/include`, is matched only by name.
- **Incomplete added inputs.** A recipe that omits a rule-built file its tool reached indirectly, such as a header found through an include path, leaves the rule stale when that file changes.
- **Undeclared inputs**, files a command's program reads without its arguments naming them, such as a config file a tool finds on its own, go unnoticed, as in every tool short of tracing tools like tup and the ptrace-based fac, or sandboxed ones like Bazel.
- **Dependencies known only after a scan**, such as the imports of C++20 modules, have no mechanism like ninja's `dyndep`, and neither does a generator that chooses its own output names, such as protoc emitting a file per service.
