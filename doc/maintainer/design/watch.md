# Watch mode

Watch mode ships before 1.0, after the graceful stop and the lock it relies on. `fac --watch NAME... [-- ARG...]` runs until interrupted and serves two goals: building on save in any editor, and live tasks such as a test run or a dev server that restart on a change. Lower latency than a fresh invocation is not a goal, and neither is editor diagnostics integration.

## Requirements

- Watch mode MUST build the given names, then build them again whenever a file the previous cycle read, or a directory it listed, changes content.
- Every name given to watch mode is something to build or a task to start. A change MUST restart every named task once the names before it are built. A task not named MUST NOT be stopped or restarted by watch mode.
- Watch mode MUST NOT start a cycle for a change that leaves every observed file's content and every listed directory's entries as they were, or for an output Facere itself wrote.
- Watch mode MUST behave identically on Linux and Windows. It MUST NOT miss a change on a file system that reports none, though it MAY notice the change later.
- A cycle that fails collection MUST keep watching what the last collected cycle observed, along with the `fac.py` files it tried to load, so fixing the mistake starts a cycle.
- Each cycle MUST end with a fixed line an editor can match. The 3-line budget for Facere's own output does not count it.

## Design

- **Supervisor.** `fac --watch app test` starts a supervisor that runs no collection and holds no lock. Each cycle, it spawns a fresh `fac app test` child, inheriting the terminal, and waits for a change. The child also gets the hidden flag `--watched`, which makes it record what it observed, below, and on Windows re-enable Ctrl-C, so neither costs an invocation outside a watch anything. With no names, the child builds the defaults, as `fac` does. A loop of in-process invocations cannot work: a task's recipe is Python in a worker thread, and Python cannot kill a thread, so a recipe that catches the error from its killed command, or serves from Python itself, could never be restarted. Django's autoreloader, iBazel, watchexec, and `deno --watch` restart processes for the same reason. A fresh process costs about 46 ms of interpreter start and imports per cycle. Every cycle collects again, so an edit to a `fac.py` or a shared module takes effect on the next one.
- **Triggers.** A cycle starts when something the previous cycle observed changes: a `fac.py` or shared module it loaded, a directory it listed, or a file it hashed, task inputs included. Nothing else does: not a store other than a `FileStore`, whose file is observed as any file, not a hidden path, a file no cycle read, or a scratch file in the output directory. The listing that [shadowing](./fingerprints.md#added-inputs) walks is not observed either, or any new file under the root would start a cycle, so a new file shadowing an added input waits for the next cycle another change starts. The supervisor confirms a change as the hash cache does, rehashing a file whose size, mtime, ctime, or inode moved and relisting a directory whose mtime moved. It counts the change only when content or entries differ from the record, so saving an unchanged buffer, `touch`, and an editor's atomic-save temporaries start nothing. A declared output whose content matches its record is Facere's own write and starts nothing, while one edited by hand starts a cycle that rebuilds it. A writer that is not idempotent, such as a task stamping the time into a globbed file, still loops, so each cycle prints the paths that started it, as in `fac: change in src/main.c, lib/fac.py`, and a narrower glob fixes the loop.
- **Detection.** The supervisor polls the observed set, since inotify misses changes another machine makes on a network file system, and under WSL2 a Linux watcher sees no edit a Windows application makes on a Windows drive. A sweep costs about 20 ms on the N100 for the 7000-file benchmark, about 4% of one core at a 500 ms interval. Native events, inotify and `ReadDirectoryChangesW` through `ctypes`, can be added later as wake-up hints over a slower safety sweep, if polling's idle cost is measured to matter, while macOS keeps polling.
- **Debounce.** After the first confirmed change, the supervisor waits until 100 ms pass with no other, so Save All and a formatter's rewrite after a save start one cycle. The quiet period takes no flag. A write landing after a cycle has started starts another, which skips every rule the first one finished. A change undone within the quiet period, as an editor's temporary file is, starts nothing. The line starting a cycle names at most three paths and counts the rest, and a directory whose entries changed ends in `/`.
- **A change during a cycle.** The supervisor sends the child the graceful stop, so a user saving every 20 s during a 60 s build still gets one finished. The next cycle rebuilds what is stale and starts the named tasks again. During a cycle the supervisor polls what the previous cycle observed, less outputs, which the cycle writes, comparing each path with what the cycle recorded of it once it has saved its record, and until then with what the supervisor saw as the cycle started. A cycle saves its record before each task, which may never end, and as each batch ends, so the first cycle of a watch, with no previous one, can be stopped only once it reaches a task, and an edit during it otherwise starts the next cycle once it ends.
- **A cycle that does not finish.** A failed collection reads none of the files that started it, so their changes would start a cycle on every sweep. Until a cycle finishes, a path counts as changed only where it differs from both what the last cycle recorded and what it held as the unfinished cycle started.
- **Task arguments.** The supervisor passes what follows `--` to every child, as in `fac --watch serve -- 8080`.
- **A server a watch restarts.** Every change stops a task that never ends, so a named server restarts on each cycle and must bind its port again at once. Reloading a browser is the project's own code, as in the `my-site` example, whose page asks the server for a hash of what it serves and so survives the restart.
- **Tasks the user owns.** A server that reloads itself, such as Vite, runs as a task in its own `fac` and calls `fac.give_lock()`, as in `fac serve` in one terminal and `fac --watch app` in another.
- **Terminal.** The child has the terminal, so tasks print live and read stdin, and on Linux and macOS Ctrl-C reaches the whole foreground process group. The supervisor reads no keys and never clears the screen. It waits for an interrupted child, then ends on a closing line of its own, `Interrupted` with status 130, and a graceful stop it is asked for reaches the child too, ending on `Stopped` with status 143.

## What watch mode needs first

- the lock the kernel releases, so a killed child never leaves one behind
- the graceful stop, which is the supervisor's only request to its child
- one audit hook per process
- output an editor can parse

## The observed set

Each cycle saves in the state what it observed, under its names, so watches of different names on one output directory keep apart: each file with the hash it found, each directory with a digest of its entries, less hidden names, and which of them lie in a declared output, so the supervisor tells Facere's own writes from an edit. The files are those the hash cache saw, task inputs included, hashed as a task starts, those collection opened, which an audit hook notes as `open` events while a `fac.py` loads, and declared inputs found missing during collection, recorded as absent. The directories are those a tree hash walked and those collection listed through `os.scandir`, which `glob`, `pathlib`, and `os.walk` use, while the import system lists `sys.path` entries through `os.listdir`, which is not observed, so a new file beside `fac.py` starts nothing unless a glob lists the root. A file collection opened is stamped as it is opened and hashed once the build has a hash cache, and one whose stamp moved between the two records a hash that matches no content, so the supervisor starts a cycle at once. Outputs of rules that failed are left out, since what a failed recipe left is stale whatever its content, and observing it would loop a recipe that writes differently each time it fails.

Only a cycle records, since an invocation that built nothing must leave no output directory, while a watch whose first cycle failed collection must still know what to wait on. A cycle that fails collection extends the saved record instead of replacing it, so the watch keeps what the last collected cycle observed. The supervisor also always observes the root's `fac.py`, so a cycle that failed before collection, as for a missing `fac.py`, is followed once it is written.

## Windows and editors

- **Ctrl-C on Windows.** The supervisor can send `CTRL_BREAK_EVENT` only to a child started with `CREATE_NEW_PROCESS_GROUP`, and that flag also disables Ctrl-C in the child and everything it starts. The child therefore re-enables Ctrl-C through `SetConsoleCtrlHandler(None, False)` at startup, so Ctrl-C behaves as on Linux and macOS.
- **Cycle markers.** A VS Code background task tracks a watcher through a `beginsPattern` and an `endsPattern`, as `tsc --watch` prints `File change detected. Starting incremental compilation...`. The `fac: change in ...` line begins a cycle, and the fixed closing line, `fac: watching for changes`, ends it. The first cycle has no change to name, so an editor's task starts active, as VS Code's `activeAtBeginning` does.
